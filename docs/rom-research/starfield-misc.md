## 1. The real starfield (Namco star circuit / "05xx")

### 1.1 Verified hardware model (research_starfield.md, entire file)

- **Hardware, not software.** "The starfield is a hardware subsystem — the Z80 ROM only writes
  scroll/freeze bits; the star positions and colours are generated by the Namco star circuit"
  (research_starfield.md:3-6). "There is NO colour or position data in the ROM" (:26).
- **Positions/colours are a FIXED TABLE, not an LFSR.** Verified against MAME `star_seed_tab`:
  - "`star_seed_tab[252]` = 4 sets x 63 stars. Each record is
    `{ x, y, colourIndex (0-63), set (0-3) }` — **fixed** positions + colours, not random."
    (research_starfield.md:66-68)
  - **The 252 records themselves are NOT transcribed anywhere in the corpus.** The table is
    named, sized, and its record shape given — the actual byte values are absent. To port it
    verbatim you must pull `star_seed_tab` from MAME `video/galaga.c` yourself.
- **Two sets visible at once (126 stars on screen):**
  - "`set_a = starcontrol[3]`, `set_b = starcontrol[4] | 0x2`; a star draws if its `.set`
    matches either. Toggling which sets are active is the **twinkle / blink**."
    (research_starfield.md:69-71)
  - Note the structure: set_a ∈ {0,1} (bit from starcontrol[3]) and set_b ∈ {2,3}
    (starcontrol[4] OR'd with 0x2). So the lit pair is always one-of-{0,1} plus one-of-{2,3}
    — 4 possible combinations, chosen by two independent control bits driven by the game,
    NOT a fixed (0,2)/(1,3) alternation.
  - **Blink period: NOT specified in the corpus.** No frame count for how often the ROM
    toggles starcontrol[3]/[4] appears anywhere in these files. The clone (zanelogi) has
    "no blink" at all (research_starfield.md:99); our 32-frame period is authored, and the
    corpus neither confirms nor refutes it.

    > **Correction (2026-08-02, found while porting the star control for fidelity
    > pass 6):** the cadence IS attested — in the disassembly itself, not the corpus
    > notes. `jp_Task_man` derives the two select bits from the global frame counter
    > every interrupt (task_man.s:362-368): bits 2-4 of `ds3_92A0_frame_cts` are
    > folded through `(c >> 1) ^ c` and masked to bits 3-4, which lands `f3 ^ f4` on
    > starcontrol[3] and `f4` on starcontrol[4]. That walks the lit pair through the
    > Gray cycle (0,2) -> (1,2) -> (1,3) -> (0,3), one step every 8 frames, all four
    > legal pairs reached and only one set changing per step. The replica's
    > `blinkBits` (src/systems/starfield.js) now implements exactly this; the
    > 32-frame both-bits toggle it replaced was authored and wrong.
- **One scroll speed — no parallax:** "One vertical scroll speed (the `$A000` bits) —
  **no parallax** in hardware." (research_starfield.md:72)

### 1.2 Colours — the 2-2-2 RGB palette (verified, MAME PALETTE_INIT(galaga))

Verbatim (research_starfield.md:50-58):

```c
static const int map[4] = { 0x00, 0x47, 0x97, 0xde };
//  R = map[(col>>0)&3]   G = map[(col>>2)&3]   B = map[(col>>4)&3]
```

- Four levels per channel: **0x00, 0x47, 0x97, 0xDE** = (0, 71, 151, 222).
- 4^3 = 64 colours at palette indices 32-95; (0,0,0) is the invisible black star →
  **63 visible full-spectrum colours** (red/green/blue/yellow/cyan/magenta/white + mixes).
- Each star carries a fixed `colourIndex (0-63)` in the seed table; colour is per-star data,
  not derived from position bits.

### 1.3 Z80 scroll control — the only software involvement

- The ROM writes the star-control port **$A000-$A005** via `c_star_ctrl`
  (task_man.s:328-382). Disasm comment: *"starfield scroll speed (only bit 0 is
  significant)"* (task_man.s:359); *"7 == star_ctrl_bits = frozen"* (task_man.s:375).
- `f_1D76` (gg1-2_fx.s:1414) sets `ds_99B9_star_ctrl[0] = 1` when the ship is on screen,
  `= 7` (**freeze**) "during attract / between events" (gg1-2_fx.s:1463;
  research_starfield.md:19-24). So:
  - **gameplay (ship on screen): scrolling down**, control value 1;
  - **attract / between events / ship off screen (death): FROZEN**, control value 7.
  - The corpus clone's own starfield.js header agrees: "Enabled: when stage begins
    (game_ctrl.s:312). Disabled: during attract / game-over (game_ctrl.s:179). Frozen: when
    ship off screen" (tasks/starfield.js:7-9). The gameController STATE_TASKS keeps
    starfield *visible* in attract (gameController.js:50) — visible but frozen.
- No absolute px/frame speed is stated for the hardware. The corpus clone approximates with
  SPEED_SLOW = 0.25, SPEED_FAST = 0.50 px/frame scaled by `starCtrl.speed` (1-4, "increases
  with stage number (set by new_stage.s)", state.js:392-395) — but the clone's 2-speed split
  is explicitly flagged as an unfaithful parallax approximation (research_starfield.md:97-98),
  and task_man.s says only bit 0 of the port value is significant, which argues against a
  meaningful per-stage speed ramp in hardware. Treat the 1-4 speed claim as unverified.

  > **Correction (2026-08-02, found while porting the star control for fidelity
  > pass 6):** the per-stage ramp is REAL and fully attested, and "control value 1"
  > above conflates two bytes. `ds_99B9_star_ctrl` is a six-byte block (mrw.s:536-542):
  > +0 is only the scroll ENABLE (1 while the fighter is on the board), while +2 is
  > the stage's speed control, written by `c_2C00` as
  > `0x40 + ((min(stage, 0x10) << 2) & 0x70)` (new_stage.s:105-117). Each frame
  > `f_1D76` (gg1-2_fx.s:1414-1453) ramps 99BC toward that control at +1 and adds it
  > into the 6-bit accumulator 99BD; the sum's two carry bits (0-3 rows) become the
  > hardware value `(-v - 1) & 7` in star_ctrl+5 — indices 7/6/5/4, whose MAME
  > speeds are 0/1/2/3 rows forward. Net: play speed averages control/64 rows per
  > frame, 1.0 at stage 1 rising to 2.0 at stage 16+, dithered by the accumulator;
  > and the enable-off path (l_1DA8) zeroes 99BC/99BD, so the scroll re-ramps from
  > a standstill after every death. Absolute px/frame IS therefore derivable, and
  > the replica's `advanceStarfield` now runs this machine verbatim.

### 1.4 Capture scroll reversal (verified, gg1-3.s + gg1-2_fx.s:1423-1447)

During the tractor-beam **pull**, stars scroll UP. Flag `star_ctrl[1]` (RAM `99BA`):
`f_1D76` reads it each frame (gg1-2_fx.s:1423-1426); when nonzero it forces the scroll to
the reverse direction (`A = 0xFD` then `neg` at :1447) instead of the normal ramped
down-scroll. Toggle points (research_starfield.md table, :36-40):

| Event | Z80 line | star_ctrl[1] | Stars |
|---|---|---|---|
| Beam latches ship, pull begins (`f_20F2` on, `captr_flag = 0x0A`) | `l_236D` gg1-3.s:691 | = 1 | UP |
| Ship reaches boss → fighter captured (`f_19B2` carry-home) | `l_2305` gg1-3.s:626 | = 0 | DOWN |
| Boss shot mid-capture (abort) | `l_2327` gg1-3.s:645 | = 0 | DOWN |

Verified reversibility property (research_starfield.md:86-88): a 40-frame down-scroll then an
equal up-scroll returns the field **exactly** to its start (63/63 stars).

> **Correction (2026-08-02, found while porting the star control for fidelity
> pass 6):** two refinements to this section.
>
> 1. The reverse path's speed is pinned, not merely "the reverse direction":
>    `A = 0xFD` through `neg / dec / and 7` (gg1-2_fx.s:1425,1444-1450) yields
>    hardware index **2**, and MAME's `speeds[2]` is **-3** — the pull runs three
>    rows per frame upward, faster than any forward play speed (1-2 rows). The
>    down-then-up restore property holds for equal ROWS, not equal frame counts.
> 2. The scrolled axis is the chip's hardware **X** — the raster's horizontal,
>    mounted vertical in the portrait cabinet. MAME adds `speeds[]` to
>    `stars_scrollx` and draws `x = (tab.x + scroll) % 256` with `tab.y` fixed
>    (historic video/galaga.c:570-571,606); the modern `starfield_05xx` device
>    wires the game's three control lines to SCROLL_X likewise. A replica that
>    scrolls the table's y is transposed: the seed table's x is the
>    screen-vertical, scrolled coordinate. `visibleStars`
>    (src/systems/starfield.js) now projects it that way.

## 2. Task scheduler / frame model

- **Z80 model:** cooperative scheduler over a fixed task table `d_cpu0_task_table`
  (task_man.s); each task runs every frame iff its enable flag in `ds_cpu0_task_actv` is
  set; tasks freely flip each other's flags; shared RAM state (CLAUDE.md:94-114). The
  scheduler runs from the ~60 Hz VBL interrupt, so background tasks keep running while
  `g_main()` blocks in spin loops on `game_state` (gameController.js:6-17).
- **Frame cadence:** fixed timestep `FRAME_PERIOD = 1000/60` with an accumulator
  (main.js:90-148); `state.frameCount` mirrors `ds3_92A0_frame_cts[0]`, a 60 Hz tick counter;
  sub-rates via `(frameCount % N) === 0`, e.g. `% 4` = 15 Hz (CLAUDE.md:117-119). Update may
  run multiple times per rAF; render once per rAF, always for every task regardless of enable
  flag ("the Z80 sprite RAM is always drawn", CLAUDE.md:110; main.js:129-133).
- **Task order** (main.js TASK_TABLE, mirrors d_cpu0_task_table order): gameController(JS),
  starfield f_1D76, formationOscillate f_2A90, formationPulse f_1DE6, objectStates f_23DD,
  bugMotion (CPU1 f_08D3), enemyStatus f_1DB3, bombUpdate f_1EA4, bomberConfig f_0857,
  launchAttackWave f_2916, bonusBee f_1A80, playerMove f_1F85, playerFire f_1F04,
  bulletUpdate (CPU1 rckt), captorDive f_21CB, tractorBeam f_2222, pullShip f_20F2,
  fighterCaptured f_19B2, explosions case_24B2, hud.
- **CPU0/CPU1 split:** bullet move/collision ran on a second CPU (rckt_man + hitd_det_rckt);
  the clone slots bulletUpdate right after playerFire so a fresh bullet doesn't move the
  same tick — "matches the natural CPU0/CPU1 1-frame lag" (main.js:38-43).
- **Always-on tasks** (`task_enable_tbl_def = 0x01`): objectStates (f_23DD) and bombUpdate
  (f_1EA4) (state.js:371-373, CLAUDE.md:241-243). f_1DD2 (game-timer decrement) is not in
  the task table at all — always-on, unconditional (main.js:44-45, 95-102).
- **Game timers:** `ds4_game_tmrs` = 4 countdown bytes decremented at **2 Hz** (every 30
  frames) by f_1DD2 (main.js:95-102). Semantics (state.js:351-359): [0]/[1] general purpose,
  [2] stage timer (set to 120 at stage start), [3] short delays (set 3/4/8). Tasks busy-wait
  on them. Stage-clear splash = game_tmrs[2]=3 at 2 Hz ≈ 1.5 s (task_man.s:227-242;
  state.js:180-183).
- **f_2A90 (oscillate) and f_1DE6 (pulse) are mutually exclusive** — one runs during
  fly-in/attack, the other at steady state (CLAUDE.md:246-249).
- **Input cadence:** raw key state sampled ONCE per logic tick before task dispatch —
  "mirrors the Z80's io_input[] polled at the top of the frame"; fire is edge-triggered
  (rising edge only), reproducing the Z80 IO chip's hardware debounce (main.js:80-84,
  105-112).

## 3. Explosions

- **Enemy death-burst** — Z80 `case_24B2` (gg1-3.s:945), disposition 4 ("exploding"):
  sprite codes **0x41-0x44** (4 frames) at **palette 0x0A** (enemyStatus.js:9-10,
  state.js:448), 16x16, drawn centered. Clone hold = **4 game-frames per animation frame**
  (spawnExplosion default holdFrames=4; enemyStatus.js:38) → 16 frames ≈ 0.27 s total.
  The 4-frames-at-4 cadence is the clone's choice; the corpus does not cite a Z80 frame-hold
  count. Burst position: enemy's live position (in-flight) or home+oscillate+pulse offsets
  (in formation) (enemyStatus.js:35-37).
- **Player explosion** — Z80 `case_243C` (gg1-3.s:850), disposition 8 (hitd_fghtr_hit →
  disposition 8; bombUpdate.js:141-142): a **2x2-sprite (32x32) burst** at the destroyed
  fighter's position, spawned with holdFrames=4 (bombUpdate.js:145,150). Frame count of the
  ship burst = length of the decoded `explosionShip` array (not stated numerically in corpus).
  twoShip: left fighter destroyed first → revert to single, burst at x-16 (bombUpdate.js:143-146).
- Animator mechanics (explosions.js): slot reuse (alive=false = free), per-entry
  {frames, frame, timer, holdFrames}; decrement timer, on 0 reload + advance frame; past last
  frame → dead. Rendered LAST so bursts sit on top of enemies/bombs (main.js:68-69).
- Sprite-state note: "sprite state b_8800 = 0x08 ('exploding')" appears for the player path
  (architecture.html:1399); a killed bug's disposition "goes to exploding/inactive, never
  back to formation" (enemyStatus.js:41-43).

## 4. Object states / sprite rendering (f_23DD)

### 4.1 b_8800 disposition codes (as attested across the corpus)

`b_8800` = 128 per-object disposition/status bytes; stage init does
`memset(b_8800, 0x80, 0x80)` — "all 128 disposition bytes 'inactive'"
(research_stage_init.md:388). Codes attested:

| Code | Meaning | Corpus citations |
|---|---|---|
| 0x80 | INACTIVE (alive-but-not-spawned / despawned; sprite hidden) | research_stage_init.md:388; bugMotion.js:215,232; research_path_data.md:83 (0xFF END token sets b_8800[id]=0x80) |
| 0x01 | STAND_BY (resting in formation; launchable) | research_attack_paths.md:171; bonusBee.js:36 ("disposition == 1 'resting'") |
| 0x03 | in path flight (F5 token `case_0942` sets disposition 3) | research_attack_paths.md:518; research_path_data.md:113 |
| 0x04 | EXPLODING (bug death-burst, case_24B2) | enemyStatus.js:6-10; explosions.js:4 |

| 0x09 | homing/diving (set at FB TURN_HOME, case_0AA0; polled by capture code `b_8800[cobj] != 0x09` as the abort cue) | research_path_data.md:260; research_attack_paths.md:273; architecture.html:461; launchAttackWave.js:106-107; captorDive.js:34; tractorBeam.js:43 |

(architecture.html:965-966,1018; research_bonus_bee.md:156; state.js:441).

### 4.2 Sprite frame selection (Z80 gg1-5.s:2104-2148, verified)

Each enemy type has 8 frames. Frames 0-5 = 6 directions in one quadrant (~15 deg/frame);
frame 6 = vertical (within +/-15 deg of 90/270); frame 7 = vertical wings-closed. Base
sprites face UP-LEFT (Q1). Frame index math (objectStates.js:28-46, Z80-verified):

```
lowByte = angle & 0xFF                      (angle is 10-bit, 1024/circle)
if (quadrant odd) lowByte = ~lowByte & 0xFF (CCW→CW within quadrant)
if (lowByte + 21 >= 256)  frame = 6         (equivalent: lowByte >= 235)
else frame = upper 3 bits of (3*lowByte/4)  (Z80: srl/srl/add → 3A/4, then 3 rlcas & 0x07)
```

Flips by quadrant (sprite-chip flip-X/flip-Y): Q0 (0-90, right-up): flipY; Q1 (90-180,
up-left): none; Q2 (180-270): flipX; Q3 (270-360): flipX+flipY (=180 deg rotation).

### 4.3 Formation idle / wing-flap

`case_2488` / `case_245F` (gg1-3.s): enemies in formation alternate sprite codes **6 and 7**
at ~1 Hz-per-full-cycle — clone: `frame = 6 + ((frameCount >> 5) & 1)` i.e. **every 32
frames** (objectStates.js:61-63; progress.html:309 records the fix; the comment says "~2 Hz
(every 30 frames)" but the code is >>5 = 32). Formation position = homeX/Y + oscillateX +
pulseOffsets (per-column X [0-9], per-row Y [10-15]) (objectStates.js:79-81; state.js:484).
Render states: 'pending' (0x80) and 'dead' are NOT rendered; 'flying'/'homing' render at own
(x,y) with angle-driven frame+flips; 'formation' renders wing-flap pair (objectStates.js:2-8).
Special skins: launched bonus-bee uses the 0x5x sprite group (colorIndex 0-2), reverting on
home-back because the 0x5x base has a blank frame 7; 2-hit boss renders blue (palette 1)
after first hit (objectStates.js:87-101). 16x16 sprites drawn CENTERED on (x,y)
(drawImage(img, x-8, y-8)); flips via canvas scale around center (objectStates.js:102-111).

## 6. Remaining portable facts (main.js / state.js / CLAUDE.md)

- **Coordinate conversions** (CLAUDE.md:124-178, galagino+MAME verified): center canvas_X =
  sprite_X - 9 (corner -16, +8 center, -1 nudge); variants sprite_X = rawX*2; canvas_Y =
  sprite_Y_byte + 256*bit8 - 32; bug-path sprite_Y = ((~(rawY+0x4F)) & 0xFF)*2 + 1. Worked
  examples: ship spawn 0x7A=122 → x=113; ship limits 0x12/0xE1 → canvas 9/216; formation
  cols [0x31..0xC1] → [40..184]; player y=265 (base flush on lives row, MAME-confirmed).
  Tile-plane/HUD positions do NOT carry the -9/-32 offset.
- **Attract flow:** Z80 g_main blocks in spin loops per state (ATTRACT → READY_TO_PLAY →
  gctl_game_runner), with the VBL scheduler running tasks (incl. f_0977 coin/start input)
  underneath (gameController.js:6-17). In attract: starfield visible (frozen per 1.3),
  formation/player hidden. The corpus clone has NO attract demo (deferred, CLAUDE.md:50).
- **Player movement fidelity:** pre-move bounds check (`cp limit / ret c` BEFORE add), not
  post-move clamp; dxFlag (`b_92A0[3]`) toggles each held frame alternating 1/2 px ≈ 1.5
  px/frame (CLAUDE.md:182-189; state.js:400-412).
- **Bullets:** max 2 simultaneous, slot scan c_1F0F (gg1-2_fx.s:1873-1884) (state.js:433-435).
- **Bombs:** 8 slots (b_8800+0x68..0x7F); vector FROZEN at drop (not homing); constant Y
  velocity 2/3 px/frame down (state.js:440-445); drop reload b_92E2[0] = 0x14 ≈ 20 frames
  (bombUpdate.js:22).
- **Fidelity patterns:** keep power-of-two mask wraps (& 0xFF / & 0x07), keep integer sprite
  codes as magic numbers with Z80 citations (CLAUDE.md:190-197).
- **Formation:** 48 slots (8 boss cols 3-6 x2 rows, 20 butterfly, 20 wasp); rows canvas Y
  28/44/60/72/84/96; cols X 40..184 step 16 (state.js:19-27; CLAUDE.md:244-246).
- **Rank display mapping** (str_3A68): rank 0=B, 1=C, 2=D, 3=A; difficulty A≈B < C < D;
  params use rotated sub-table bmbr_stg_cfg_lut (3→0, 0→1, 1→2, 2→3) (state.js:166-174).

## 7. GAP LIST (ranked)

Starfield (src/systems/starfield.js):

1. **Star positions/colours should come from the fixed MAME `star_seed_tab[252]`
   ({x, y, colourIndex 0-63, set 0-3} per record), not an LFSR.** Our whole generation model
   is an approximation of the wrong kind of source (fixed ROM-equivalent data vs PRNG). The
   table's values are NOT in this corpus — must be transcribed from MAME video/galaga.c.
2. **Colour levels are wrong.** Real 2-bit gun map is {0x00, 0x47, 0x97, 0xDE} =
   (0, 71, 151, 222); ours is [70, 130, 190, 255] — no true-black level, wrong steps, so
   the sky is uniformly too bright and never has the dim first-level stars.
3. **Attract-mode scroll should be FROZEN (star_ctrl = 7), not a 0.35-row drift.** Verified:
   ship-on-screen = 1 (scrolling), attract/between-events = 7 (frozen)
   (gg1-2_fx.s:1414/1463; task_man.s:375). Our STARFIELD_SCROLL.title = 0.35 contradicts it.
4. **Set-selection semantics:** lit pair = (starcontrol[3] ? 1 : 0) + ((starcontrol[4]|0x2)),
   i.e. one of {0,1} plus one of {2,3}, game-driven — not a hardwired (0,2)/(1,3) 2-phase
   toggle. Our 32-frame period is unattested (corpus has no blink period at all); keep it
   authored but restructure selection as two independent bits so all 4 combos are reachable.
5. **Capture-pull reversal wiring:** stars scroll UP exactly from beam-latch (l_236D) to
   capture-complete (l_2305) or boss-shot abort (l_2327), via star_ctrl[1] → value 0xFD/neg.
   Our field supports negative rowsPerFrame, but whoever drives it must key on exactly that
   window, and down-then-up must return the field exactly to start (verified property).

## 8. Porting recommendation

1. **Transcribe `star_seed_tab` from MAME** (historic-mame `src/mame/video/galaga.c`) — 252
   records — and replace `createStarfield`'s LFSR sampling with the table. Keep the LFSR
   module only if we want a documented "authored fallback" behind a flag; the corpus is
   unambiguous that the real model is fixed data. This is the single change that makes
   star positions/colours pixel-comparable to MAME.
2. **Fix `starColor` levels to [0x00, 0x47, 0x97, 0xDE]** regardless of decision 1 — it is
   a 4-line change and removes the visibly-wrong brightness quantisation now.
3. **Change scroll semantics to a 3-state control** mirroring star_ctrl: RUN(1)/FREEZE(7)
   plus the reverse flag (star_ctrl[1]) — attract and death freeze; play scrolls down; the
   tractor pull window reverses. Drop the title-drift speed; keep one game speed (single
   scroll plane, no parallax — we already have that right).
4. **Restructure blink as two set-select bits** (set_a ∈ {0,1}, set_b ∈ {2,3}) toggled on
   our existing 32-frame counter (documented as authored, since no verified period exists).
5. Lower priority: audit the rest of the replica against §6-§7 items 6-9 (disposition codes,
   sprite-angle rule, explosion specs, 2 Hz timers) — these are scheduler/gameplay-fidelity
   items outside starfield.js and each is fully specified above with citations.
